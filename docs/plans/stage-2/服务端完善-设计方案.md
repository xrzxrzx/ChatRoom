# Stage 2 实施方案：服务端稳定性完善

## 一、目标

解决服务端"连接即断、发送者重复收消息、房间人数不实时、无心跳、配置硬编码"等稳定性与体验问题。

## 二、当前状态

1. `do_accept` 不持有会话，`shared_ptr` 局部变量析构后连接被关闭（B2）。
2. 广播包含发送者本人（B8）。
3. 房间初始化散落在构造函数与 `Main.cpp`（B10），且 `AddChatRoom` 使用 `static id`。
4. 无心跳、无 leave_room 通知、无房间人数更新事件。
5. 端口 `12345`、gRPC `localhost:50051` 硬编码。

## 三、方案细节

### 3.1 会话持有与生命周期

`ChatServerService` 增加：

```cpp
std::unordered_map<int, std::shared_ptr<UserSession>> sessions; // 以 userId 或 socket 句柄为键
```

- `do_accept` 创建会话后加入容器（连接尚未登录时以内部递增 id 占位）。
- `UserSession` 增加 `OnClosed` 回调（或由 service 传入清理函数），读错误/EOF 时：
  1. 从当前房间移除并广播 `leave_room`；
  2. 从 `sessions` 容器移除自身；
  3. 广播 `update(room_list)`。
- 会话内回调统一捕获 `shared_from_this()`，避免悬垂 `this`。

### 3.2 发送者过滤

`ChatRoom::Broadcast` 增加可选排除参数：

```cpp
void Broadcast(const EventMessageBag& event, const std::shared_ptr<UserSession>& exclude = nullptr);
```

`HandleSendMessage` 广播时传入 `shared_from_this()` 排除本人；本人消息由 API 响应回显。

### 3.3 房间初始化

- 构造函数仅保留空房间表；默认房间列表移入配置文件（`rooms` 数组），`AddChatRoom` 用成员 `nextRoomId` 递增。
- 删除 `Main.cpp` 中 `StartAccept()` 之后不可达的 `AddChatRoom` 调用。

### 3.4 心跳

- 服务端每 30s 向所有已登录会话发送 `heartbeat` 事件（含服务端时间戳）。
- 客户端收到后回发 `heartbeat` API（或服务端通过读事件天然活跃判断：若 90s 无任何数据则断开）。
- 简化方案：服务端维护 `lastActivity`，定期扫描超时连接并清理。

### 3.5 房间人数更新事件

加入/离开房间成功后，向所有房间成员（或全局）广播：

```json
{"post_type": "update", "data": {"update_type": "room_list", "update_data": [...]}}
```

客户端据此更新 `RoomInfoList` 中对应房间的 `user_count`。

### 3.6 配置化

新增 `server.json`（默认值内置于代码）：

```json
{
  "port": 12345,
  "grpc_address": "localhost:50051",
  "heartbeat_interval_sec": 30,
  "idle_timeout_sec": 90,
  "max_message_length": 4096,
  "rooms": ["通用", "游戏开黑", "技术交流"]
}
```

`UserSessionServiceClient` 改为从配置注入 gRPC 地址（去掉 TODO）。

### 3.7 房间创建与动态生命周期（新增需求）

#### 3.7.1 `create_room` API

| 项 | 内容 |
| ---- | ---- |
| action | `create_room` |
| 请求参数 | `room_name: string`（非空、≤32 字符） |
| 返回数据 | `room_id: int32`、`room_name: string` |
| 错误码 | `400` 参数非法（空名/超长）、`409` 房间名已存在 |

处理流程：
1. 校验房间名合法性（非空、长度 ≤32、不与现有房间重名）；
2. `ChatServerService::CreateChatRoom(name, ownerUserId)` 创建 `ChatRoom`（`isSystem=false`），分配 `nextRoomId`；
3. 将创建者自动加入该房间（复用 `JoinChatRoom`）；
4. 返回 `room_id/room_name`，并向所有在线客户端广播 `update(room_list)`。

#### 3.7.2 房间生命周期

- `ChatRoom` 增加 `bool isSystem`（系统房间 `true`，用户创建 `false`）。
- 成员离开（断开、退出、换房）触发 `RemoveParticipant` 后，若 `!isSystem && GetUserCount()==0`，则：
  1. 从 `chatRoomMap` 移除该房间；
  2. 广播 `update(room_list)`（房间被移除）。
- 系统默认房间（配置文件 `rooms` 中的初始列表）标记 `isSystem=true`，即使无人也常驻。

#### 3.7.3 房间列表更新事件

`update(room_list)` 的 `update_data` 由当前全量房间列表构成（`room_id/room_name/user_count`），客户端以全量替换方式刷新，天然覆盖新增与移除场景。

## 四、技术选型

- 保持 Boost.Asio 单线程事件循环，不引入线程池（当前规模足够）。
- 配置解析使用 nlohmann/json（已依赖）。

## 五、接口/数据设计

### 新增/变更事件

| post_type | 场景 | 说明 |
| --------- | ---- | ---- |
| notice + notice_type=leave_room | 用户离开 | 原 join_room 对称补充 |
| update + update_type=room_list | 房间人数变化 | 新增，广播 room_id/room_name/user_count |
| heartbeat | 保活 | 新增，data.time 为服务端时间戳 |

### 配置结构

见 3.6，全部字段可选（有默认值）；`rooms` 数组中的房间标记为系统房间（常驻）。

### 新增 API：create_room

见 3.7.1：请求 `room_name`，返回 `room_id/room_name`，错误码 `400/409`。

## 六、影响范围

- `ChatRoom.Server`：`ChatServerService.h/cpp`、`UserSession.h/cpp`、`ChatRoom.h/cpp`、`Main.cpp`、`UserSessionServiceClient.cpp`、新增 `ServerConfig`。
- 客户端：Stage 3 需配合处理 `update`、`heartbeat`、`leave_room`。
- 客户端：Stage 3 新增创建房间 UI，并支持 `update(room_list)` 全量刷新（新增/移除房间）。
- 文档：`docs/event.md`。

## 七、测试策略

- C++ 逻辑测试（可选）：房间人数、广播排除逻辑拆分为可单测组件。
- 集成验证：双客户端互发、加入/离开房间、断网后会话清理、心跳日志观察。
- 配置验证：修改端口后服务端监听新端口。
- 功能验证：客户端 A 创建房间并自动加入；A 退出后房间从列表消失；系统默认房间始终存在。

## 八、验收标准

- 连接不再被立即断开；多客户端并发收发正常。
- 本人消息不重复显示；他人消息正常显示。
- 房间人数随进出实时更新；离开通知生效。
- 死连接在 idle 超时后被清理。
- 端口/gRPC 地址可配置。
- 客户端可创建房间；用户房间空置自动关闭；系统房间常驻。

## 九、风险与回滚

- 风险：会话容器与异步回调的竞态（单线程 io_context 内实际为顺序执行，风险可控）。
- 回滚：会话持有与心跳为独立提交，可单独 revert；配置改动带默认值，不影响旧启动方式。
