# Stage 1 实施方案：认证与会话链路修复

## 一、目标

解决当前"认证形同虚设、登录后身份恒为 0、客户端不携带 token"的三端不一致问题，让会话校验真实生效。

## 二、当前状态

1. `gRPCUserSession.go` 中 `ValidateSession` 返回 `IsTokenExpired(...)` 的结果，语义反转：任何过期/非法 token 都会被当作有效，而有效 token 反而被判无效。
2. C++ `HandleLogin` 未设置 `userId`；登录响应不含 `user_id`，而客户端依赖 `user_id`。
3. 客户端 `ChatRoomService` 不保存 `session_token`，全部 API 以空 token 调用；注册时多余发送 `user_id`。

## 三、方案细节

### 3.1 Go：修正 ValidateSession

```go
func (server *Server) ValidateSession(ctx context.Context, req *ValidateSessionRequest) (*ValidateSessionResponse, error) {
	response.IsValid = !JWT.IsTokenExpired(req.SessionToken)
	return &response, nil
}
```

同时补充单元测试（有效 token / 过期 token / 伪造 token）。

### 3.2 Go：修正 main.go

```go
if err := server.Serve(lis); err != nil {
	log.Fatalf("gRPC 服务终止: %v", err)
}
```

### 3.3 C++：登录身份写入与响应补全

`HandleLogin` 成功后：

```cpp
this->userId = rpcResponse.user_id();
this->nickname = rpcResponse.nickname();
responseBag.AddData("user_id", this->userId);
responseBag.AddData("session_token", rpcResponse.session_token());
responseBag.AddData("nickname", this->nickname);
```

### 3.4 C++：按 token 校验身份

`ValidateToken` 不再依赖会话内 `userId`，而是通过 `GetSessionInfo(sessionToken)` 获取 token 声明的 `user_id`，若与请求方会话身份不一致则拒绝（会话身份在登录时已写入）。

### 3.5 客户端：token 管理

- `ChatRoomService` 增加私有字段 `sessionToken`。
- `LogInAsync` / `RegisterAsync` 成功后保存 `response.Data["session_token"]`。
- 内部统一走 `CallAPIAsync(apiName, sessionToken, params)`；对外签名保持不变。
- `LogOutAsync` 使用保存的 token 调用 `logout`，成功后清空 token。

### 3.6 客户端：注册对齐协议

`RegisterAsync` 移除 `user_id` 参数，仅发送 `password`、`nickname`；用户 ID 以服务端响应为准。

## 四、技术选型

- 保持现有技术栈不变（JWT HS256 / gRPC / Boost.Asio / .NET 10），仅修正逻辑，避免引入新依赖。
- Go 测试使用标准库 `testing` + `sqlmock`（已有）。

## 八、验收标准

- `go test ./...` 全部通过。
- 登录响应包含 `user_id`；客户端登录后后续请求均携带有效 token。
- 伪造/过期 token 请求返回 `recode=502`。
- `docs/api.md` 与实现一致。

## 九、风险与回滚

- 风险：客户端 token 字段在 UI 层透传链路较长，容易遗漏调用点。
- 应对：`CallAPIAsync` 在 `ChatRoomService` 内统一封装，禁止 UI 层直连网络。
- 回滚：本阶段改动相互独立，可分别 revert 对应提交；Go 与 C++ 改动不破坏旧协议字段（新增字段兼容）。
