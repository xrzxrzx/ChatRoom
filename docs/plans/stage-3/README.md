# Stage 3：客户端健壮性完善

> 状态：⏳ 待批准 | 预估工时：1~1.5 天

## 一、阶段目标与范围边界

**目标**：修复客户端关键缺陷（B4/B6/B7/B14），完善断线重连、事件分发与交互体验，使客户端与 Stage 1/2 的服务端改动配套可用。

**范围**：
- .NET Core：事件总线订阅/派发键统一、响应等待项清理、Dispose 实现、心跳/update/leave 事件处理。
- 客户端 UI：消息发送者 ID 解析、发送 Enter 快捷键、消息自动滚动、连接状态提示。

**范围外**：服务端逻辑（Stage 2）、安全（Stage 4）。

## 二、前置条件

- Stage 1 完成（token 链路正确）；Stage 2 完成更佳（事件类型配套）。

## 三、详细任务清单

- [ ] 3.1 修复事件总线：订阅键统一为 `post_type`（小写），移除按类名订阅
- [ ] 3.2 修复 `ChatRoomFunction.OutputMessage`：发送人 ID 解析改为 `Data.Value<int?>("sender")`
- [ ] 3.3 实现 `Dispose`：`ChatClientService`、`ChatClientAPIService`、`ChatClientEventService`、`ChatRoomService` 释放资源并取消订阅
- [ ] 3.4 `ChatClientAPIService.OnResponseReceived` 完成后移除等待项（`TryRemove`）
- [ ] 3.5 重连机制：接收循环异常退出后，若未主动断开则自动重连；重连成功后重新登录（保存的 token 校验/或提示用户重新登录）
- [ ] 3.6 事件总线提供 `Unsubscribe`；关闭时完成通道读取
- [ ] 3.7 处理 `update(room_list)` 事件：更新房间人数
- [ ] 3.8 处理 `notice(leave_room/join_room)` 事件：输出系统消息
- [ ] 3.9 处理 `heartbeat` 事件：客户端回发心跳（配合 Stage 2）
- [ ] 3.10 UI 交互：回车发送、消息列表自动滚动到底部、断开/重连状态提示
- [ ] 3.11 消息发送失败或未加入房间时给出明确提示（已有部分，补充空 token 场景）
- [ ] 3.12 创建房间 UI：房间列表区域增加"创建房间"按钮与命名输入对话框
- [ ] 3.13 创建成功后自动刷新房间列表并加入新房间
- [ ] 3.14 `update(room_list)` 支持全量刷新：房间新增/移除/人数变化均正确反映（配合 Stage 2）

## 四、验收标准

- [ ] 双客户端互发消息，双方均实时显示，且无重复、无 ID=0
- [ ] 房间人数随其他客户端进出实时变化
- [ ] 断开服务器后客户端提示并自动重连（或明确提示重新登录）
- [ ] 应用退出/窗口关闭时 `Dispose` 不抛异常
- [ ] 回车可发送消息；新消息自动滚动到底部
- [ ] 可创建房间并自动加入；他人创建/关闭房间时列表实时增删

## 五、风险与应对措施

| 风险 | 应对 |
| ---- | ---- |
| 事件总线改动影响消息显示 | 增加 Core 层单元测试（订阅→发布→回调） |
| 自动重连涉及登录态恢复 | 重连后优先复用 token；token 失效则提示重新登录，不静默失败 |
| UI 线程调度 | 事件回调统一通过 `DispatcherQueue` 切换 UI 线程后更新集合 |
